整理 v6 原型送出後，主管的三點反饋，以及設計方的完整說明與頁面規劃，作為 v7 改版方向的起點。

2026/06 第一次討論 主管回饋 v7 起點
01
討論背景
Context
›
送出背景

v6 原型是設計方參考主管提供的 PPT（Slide P20–24）與原本體驗中心網站架構，自行調整改版。並沒有明確討論過文案、資訊架構，或每個頁面的精確內容。送出的目的是先丟一個畫面讓主管參考方向。

v6 內部的文案與 CTA 皆已請協助擬定，並對照 Excel 場景文案調整。整體架構依照 GA 數據洞察（最大流失在選角色步驟）做了流程簡化。

設計方的核心考量

這個網站的使用情境有兩種可能：一是從其他商品頁導流過來的使用者（有一定意圖），二是完全陌生、意圖不明的使用者直接進入。

兩種情境都要能順暢體驗，這是 v6 設計時的基本假設。因此在 P1 加入了來源說明、身份引導，以及多個「我現在要幹嘛」的定向輔助。

主管三點回饋
待回應
›
01
每個畫面先有 Layout
在生成 HTML 之前，應先有明確的線框稿（Wireframe），定義每個頁面的版面結構——哪裡放標題、哪裡放卡片、比例怎麼分。主管希望先確認架構再開始執行。
流程建議
02
畫面有一層又一層的容器感
AI 生成的 HTML 過度使用容器與 border，導致視覺上有巢狀感、缺乏呼吸空間。以附圖 P2 為例：HUD 有框、身份確認橋接有框、場景卡有框、標籤有框，整個畫面視覺顯得擁擠。
視覺問題
03
資訊重複，內容太多，重點不清楚
以 P2 為例：HUD 顯示「你的職能：業務」、Sticky header 顯示「業務的推薦場景」、橋接列顯示「你是業務」，三個地方說同一件事。主管表示需要先梳理每個畫面的資訊，優化後再給設計方執行。
內容問題
後續工作流程共識
主管
「這部分我再把每個畫面的內容優化好後再給你。」
設計方
等主管整理好每個畫面的內容規劃。收到後先做 Wireframe 確認版面，再開始生成 HTML。流程：內容確認 → Wireframe 確認 → HTML 生成 → 微調。

設計方的頁面規劃說明
Design Intent
›
設計核心邏輯

整個網站的目的是引導使用者確立身份與場景，進而體驗產品。使用者容易出現「我現在要幹嘛」、「我應該點什麼」的困惑，因此每個頁面的設計重點是降低認知負擔，不是增加資訊。

逐頁設計意圖

歡迎大廳 + 選定職能（合併）

05
補充說明：v6 設計決策背景
Why We Did This
›
為什麼流程這樣設計

v6 的架構是參考主管 PPT Slide P20–24，並對照原本體驗中心的舊版網站做的改版。核心出發點是 GA 數據：原版體驗完成率只有 12%，最大流失在「進入體驗 → 選擇角色」這一步，掉了 72%。

因此改版的核心邏輯是：降低前幾步的認知摩擦，讓使用者能更快進入產品體驗（P4），而不是在前置步驟就放棄。

為什麼加了那麼多「身份定向」的元素

使用者來自廣告導流，進來時可能不清楚「這個頁面要我做什麼」。

這也是主管回饋說「太多重複資訊」的根本矛盾——我們加了很多定向輔助，但每個都用了邊框和容器，視覺上就變成資訊爆炸。這是接下來需要用 Wireframe 先解決的問題。

主管回饋的根本問題

主管說的「一層又一層的容器感」和「資訊重複」，本質上是同一個問題：

同樣一個資訊（使用者的職能身份），在 HUD、sticky header、橋接列三個地方同時出現，而且每個都用了有邊框的元件呈現。去掉重複不是去掉功能，而是讓剩下的一個說得更清楚。

這需要主管先確認「哪一個地方是主要的身份確認點」，再由設計方調整，不能由設計方單方面決定刪掉哪個。
